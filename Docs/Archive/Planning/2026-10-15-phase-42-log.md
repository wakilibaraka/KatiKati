# Phase 42 — the rail packs at the Dock's spacing, the Dock's icons on the bar

> Owner 2026-10-15, two rail screenshots attached: *"use the mac dock spacing and look for the icons in
> dock"*. Asked to choose between readings, the owner picked **mirror the system Dock's pinned apps** and
> **match the Dock's size and pitch**. Log written at slice end (not per step — see §Notes).
> Plan: `HYBRID_PLAN.md` §Phase 42.

## The reference, measured before any code

Not from memory and not from `tilesize` alone: the owner's side Dock was probed through its own
accessibility tree (ApplicationServices, read-only), which gives what the Dock really lays out:

- `com.apple.dock` → `tilesize = 36`, no `magnification` key, `persistent-apps` = 9 pinned apps in this
  order: Safari, Chrome, Messages, WhatsApp, Mail, Terminal, App Store, System Settings, OpenCode
  (+2 `persistent-others`: the Downloads folder and the Trash).
- The Dock's `AXList` is 50 × 707 at x 1710 with its tiles **38 pt** tall on a **38 pt pitch** — i.e. 2 pt
  between two icons — and the first tile 3.45 pt inside the list's end.

So "the mac dock spacing" is `tile + 2`, `3.45 pt` of end clearance — and 2 pt is already the bottom bar's
`ChipPillMetrics.chipSpacing` ("aligned with the native icon pitch"), which is why the rail's 4 pt was the
odd one out.

## Scope in

- **42a** Rail spacing from those numbers: `IslandChrome.railChipSpacing` 4 → **2**; new
  `IslandChrome.railContentInset` = **4**; the strip's rail padding, the solver's fixed-island chrome and
  `PanelGeometry.stripTargetFrame`'s rail path all read it; the rail thumbnail card too.
- **42b** The Dock's pinned apps as launcher chips: `NativeDockPinnedApps` (decode + read),
  `KeptAppStore.dockPinnedBundleIDs`, `AppDelegate.startTaskbarRuntime` reads it, `StripOrderStore`'s
  providers include it, `DockStripView+Projection` folds it into the existing launcher list.
- **42c** The rail's cards are square: `ChipPillMetrics.cardFrameHeight(scale:onRail:)` + `railTile:` on
  `ChipView` / `LauncherChip` / `ShelfChip` / `PinnedFolderChip` and the drag-in placeholder, so a rail's
  tray pitch is the bottom bar's 42 rather than 56. (Owner asked for exactly this after seeing 42a live.)

## Scope out

- The rail's **tile size** is not taken from `tilesize` (open as 42d): it is 40, the number the code already
  documents as the native Dock's `tilesize`, and it is read by every rail chip's hover/threshold math, the
  chip views and the solver's stride at once.
- `IslandChrome.contentInset` (the bottom bar's 16) is untouched: there the inset must be ≥ the plate corner
  radius, or the rounded clip cuts a chip — `testContentInsetClearsThePlateCorner` still pins that.
- No new setting, switch, string, dependency or file: `project.pbxproj` untouched, `NativeDockPinnedApps`
  lives in `NativeDockPreferencesService.swift`, the file that already owns `com.apple.dock` reads.
- No `Tile`-to-Dock reorder: the pins append after our own kept apps (that is what the order store's
  `eligibleOrder` gives them), not at the head.

## Decisions taken with the owner (before any code, Standing Rules §1.4)

1. The Dock's pinned apps appear on the bar (running or not) — the Dock is the record, so we re-read it and
   never persist it ourselves.
2. The rail's **proportions** come from the Dock (2 pt gap, 4 pt ends), not from hard-coded new numbers.

## Notes

- **The placement flip is a settings write, so it was done with the app quit.** Kill → edit the plist →
  `killall cfprefsd` (the app's own cache would otherwise win) → launch → measure → kill → restore the
  original bytes → launch → re-read the key. Nothing else in the domain was touched, and the value was
  written from the bytes saved before the flip, not retyped from the JSON.
- **The script's background child does not survive its shell.** `build_and_run.sh --launch-trace` starts the
  executable with `&` and exits; launched that way from a tool session the app died with the session (the
  build log and the probe file stayed empty, which is how it was caught, not assumed). The app was then
  started as a supervised background process at the same bundle path, which is where the geometry above was
  measured. Worth knowing for the next live check: `--verify`'s LaunchServices path is fine, a shell `&`
  inside a short-lived command is not.
- **The AX tree is the instrument that showed this phase working**: the strip's chips expose
  `AXDescription`/`AXHelp` (app names) and `AXImage` frames, and the islands expose their plate windows — so
  the pitch, the island lengths and the chip list are all readable without a screenshot.
- §1.8's per-step cadence was not met again (one session, notes at slice end) — same recorded deviation as
  Phase 12 and Phase 41.
